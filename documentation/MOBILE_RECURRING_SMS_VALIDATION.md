# Mobile review and recurring SMS corrections

Work is local on `feature/8-android-sms-transaction-sync`, based on `ba24d2e`. No real inbox, database, screenshot, signing key, package identity or version was changed. All new SMS examples use fictional merchants, amounts and suffixes.

## Implementation and financial safeguards

1. **Swipe failure:** the previous SMS directive emitted threshold events but neither captured the pointer nor translated a card. The new directive adapts Reminders' captured-pointer, resisted offset (`0.9`, capped at 120px), 55px completion threshold and translated foreground/underlay pattern. Vertical/diagonal cancellation is stricter; edge starts and nested controls remain available. Right swipe opens the existing review modal, or the recorded transaction for resolved items. The directive has no financial approval dependency.
2. **Dismissal and Undo:** left swipe atomically marks pending/deferred/error evidence `IGNORED` and read. The existing candidate ID remains the deduplication tombstone. Matched/imported state, transaction binding and automatic-link provenance remain intact; only read metadata changes. Snackbar Undo lasts 7,000ms and restores the exact prior state, read timestamp and decision metadata using a compare-and-set on the dismissal marker, timestamp, expected state, read timestamp and transaction binding. Expired/repeated Undo and newer decisions cannot restore an obsolete snapshot. Read actions and explicit decisions advance a monotonic revision timestamp. No ledger, EMI or recurring-rule write occurs in dismissal or Undo. Existing SnackbarService presents the latest action; tokens remain independent.
3. **Checkboxes and Auto-lock:** both new Settings rows now use `.toggle`. Settings and SMS hide/read controls share a Sass checkbox mixin: a 20px visible square inside a 44px input target, existing focus treatment, theme variables and forced-color support. Auto-lock uses its existing custom picker with a hidden visual label beside the visible row label; it wraps when needed.
4. **SMS actions:** pending rows pair green Review & add (or Review details for evidence-only events) with outlined Mark read/unread. Processed rows pair View transaction with the read action. Buttons share height and available width; merchant text wraps independently. Processed rows retain a separate 44px SMS-evidence control for reconciliation details.
5. **Recurring classification:** parser v3 introduces `SCHEDULED_CHARGE`, deliberately absent from financial ledger mappings. Upcoming/scheduled charges and standing-instruction registration cannot create purchases. Completed charges and executed mandates remain purchase evidence; failed/declined attempts are rejected and reversals remain refunds. Native delivery, model validation, filter allowlists, picker types and labels include the new kind. No database schema change is needed.
6. **Existing occurrences:** the existing store already materializes and persists recurring occurrences in `card_transactions`, with `recurringRuleId` and `generatedOccurrenceDate`. Reconciliation reads those persisted rows, using existing source identity, integer amount, currency, explicit local date, time, merchant/reference and competing-claim safeguards. A supplied generated occurrence date must agree with the event date. Ambiguous recurring rows say “Possible existing recurring transaction” and require selection. The schedule never supplies proof of completion; SMS matching does not advance a rule, mark an installment paid, or add another occurrence.
7. **Merchant and related evidence:** payment clauses (`for … has been charged`, `by … on …`) take precedence over generic `at` extraction. T&Cs, management instructions, support text and URLs cannot become titles. An optional SI reference is separate from a transaction reference. Scheduled/completed evidence can be related only with matching amount/currency, explicit cycle date, compatible card/issuer and merchant, with no conflicting SI identifiers. Their fingerprints remain distinct.
8. **Legacy pending candidates:** pre-v3 purchase extraction cannot prove whether “charged” was future or completed. Such candidates are blocked from financial approval and automatic matching until the existing explicit, bounded original-message recheck recovers trustworthy evidence. Recheck preserves candidate IDs/read flags and only updates pending evidence; terminal decisions and financial records are retained. An unavailable original stays unverified. No automatic reversal or guessed merchant repair is performed. Parser-version gating also does not invalidate a previously resolved automatic relationship; that record stays available for explicit inspection.

## Date investigation

9. The Kotlin date parser returns the explicit local date and a corresponding instant; queue JSON carries both. Candidate staging preserves the instant and extracted date, filtering uses the event date, and display formats the instant. Recurring generation uses each rule's occurrence date and does not replace the SMS date. Fictional July and October messages retain their distinct dates/fingerprints even when both arrive in October. The supplied corpus also has separate July and October confirmed-charge examples. No supplied corpus SMS text or oracle was changed; the existing 70 cases contain no “will be charged” case, so new native fixtures cover that regression. Screenshots alone cannot prove the two displayed candidates are the same evidence/cycle. Without the private candidate/provider records, the actual discrepancy cannot be resolved. No date was silently rewritten.

## Navigation, preferences and accessibility

10. Single/Multiple and the three inbox segments now share CSS selectors, active state and dimensions. Selection persistence and OR semantics remain unchanged. Hide already added uses the shared checkbox target and full clickable label; its first text line aligns with the visible square when enlarged text wraps.
11. The unset-budget message is an Angular Router link to `/settings#monthly-budget`. Settings waits for its rendered view, stable input reference and database readiness before focusing and scrolling the input; there is no navigation timeout. Existing section navigation and Back history remain available.
12. Budget remains solely in SQLite `monthly_budget_minor`, with `budget_cycle_start_day`. Real encrypted BackupService round trips verify saved values, reload, a newly constructed store, restore, and older backups lacking both keys. An unset budget remains zero; a missing cycle day now resets to day 1 instead of retaining a pre-restore signal value. Currency remains INR in the synthetic regression. Existing currency-formatting tests remain in the suite.
13. Settings section buttons now use text/underline selection and compact wrapping, with no filled selection background or horizontal scrolling. Existing focus/scroll actions remain intact. No unrelated dashboard/EMI calculations or financial generation rules were redesigned.
